FlowMonitor

A multi-node RS-485 monitoring and safety-control system I designed and built for active Ion Beam Lab equipment — logging live sensor data and firing automated alerts the moment a fault is detected, so nobody has to watch a screen to know the lab is running safely.

01 · Problem & Context

Why this needed to exist

Ion Beam Lab equipment depends on steady liquid flow and stable temperature to run safely. Losing either without someone noticing quickly is a real risk. I needed a way to watch multiple pieces of equipment continuously, catch a developing fault immediately, and get that information to lab staff — without anyone having to stand in the room reading gauges or babysit a terminal.

That's the requirement FlowMonitor answers: it reads every piece of monitored equipment continuously, decides on its own whether something is wrong, and tells a person — by email, and on a dashboard reachable from any browser on the lab network — without anyone needing to be watching in real time.

Requirements

  • Independent per-equipment monitoring — each piece of equipment gets its own node, not one shared sensor.
  • Automatic fault detection — the system decides when something's wrong; nobody has to notice manually.
  • Remote alerting — lab staff find out by email, wherever they are.
  • Live visibility without special access — a browser on the lab network is enough; no terminal, no touching the hardware.
  • Local safety independent of software — a hardware relay and a manual bypass switch at every node, so the physical safety layer doesn't depend on the Python process staying alive.
  • Historical record — every reading logged, not just the current value.
Formal accuracy/response-time targets aren't documented yet — pending.
02 · System Architecture

How the system fits together

Every piece of monitored equipment gets its own Arduino Nano node. All nodes share a single RS-485 bus back to a mini PC, which runs two Python programs: one that watches the bus and handles logging and alerts, and one that serves a live dashboard.

03 · Hardware

What's inside each node

Every node is built around an Arduino Nano and carries the same seven components, so any node can be swapped or added without redesigning anything.

Fig. 2 — Per-node hardware: same seven components on every node
Flow SensorMeasures liquid flow rate — the primary signal the whole system exists to watch.
MAX31855 + ThermocoupleTemperature measurement alongside flow, on the same node.
RelayA hardware safety cutoff that doesn't depend on the Python layer staying alive to act.
BuzzerLocal audible alarm for anyone physically near the equipment.
Bypass SwitchManual override so lab staff can act without waiting on software.
OLED DisplayLocal status readable at the equipment — no computer needed.
MAX485RS-485 transceiver — puts this node on the shared bus.
Design Decision — Why RS-485

I used RS-485's multi-drop topology so every node — three confirmed so far, with more added as the lab's equipment grows — shares a single two-wire line back to the mini PC, each addressed by its own node ID, instead of running a dedicated cable from every node individually.

RS-485's differential signaling also holds up better over longer cable runs and in electrically noisier environments than a single-ended option, which matters in a lab full of running equipment.

04 · Software & Data Pipeline

What runs on the mini PC

Two Python programs run continuously on the mini PC: FlowMonitorCode.py, which owns the bus, the log, and the alerts, and dashboard.py, a Flask server that turns the latest state into a live web page.

Fig. 3 — Data flow: one reading, from sensor to alert or dashboard

FlowMonitorCode.py

I wrote this as the system's continuously-running core. It polls every node on the bus, logs each reading to a daily CSV file, checks the reading against the fault rules, sends alerts when a rule is tripped, and watches for a node going silent.

dashboard.py

A small Flask server that turns the current state into a live page — lab staff open a browser on the lab network and see the system's status, no terminal or direct hardware access needed.

05 · Fault Detection & Alerting

What counts as a fault, and what happens next

Two conditions trigger an alert. Both are checked continuously by FlowMonitorCode.py:

Low flow > 10 minutes If a node's flow reading stays below normal for more than ten minutes, an alert fires.
Node goes offline If a node stops responding on the bus, that's treated as a fault on its own — silence isn't assumed to be fine.

Alert policy

  • Every alert email has that day's CSV log attached, so the fault has context, not just a headline.
  • A 30-minute cooldown between repeated alerts for the same condition, so a sustained fault doesn't flood the inbox.
  • A startup confirmation email fires when the system boots — a working system announces itself instead of going silently online.

07 · Testing & Reliability

How I brought it up

I validated the system node by node instead of all at once. Node 1 came online first — RS-485 communication, the Python monitoring program, CSV logging, email alerts, the heartbeat watchdog, auto-reconnect, the OLED display, and MAX31855 temperature sensing all confirmed working on that single node before I added Node 2, then Node 3 and additional nodes, then the temperature and multi-node dashboard views.

Built-in reliability

  • Heartbeat watchdog — detects when a node stops responding, rather than assuming silence means nothing's wrong.
  • Automatic reconnect — a node that drops off the bus rejoins on its own instead of needing a manual restart.
