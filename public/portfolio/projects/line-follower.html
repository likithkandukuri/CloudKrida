Line Follower Robot

A priority-steering line-follower built to move quickly without losing the line as lighting changed or got covered — four IR sensors, each calibrated with its own threshold, feeding a 9-step priority cascade that decides how hard to turn.

Most Creative Build — UAlbany Showcase 2026, 20 teams
Event UAlbany Showcase, April 2026
Result Most Creative Build, 20 teams
Sensors 4 × analog IR, independent thresholds
Stack Arduino · IR Sensors
01 · The Problem

Reliable tracking, at speed, under changing light

IR line sensors work by reading reflected infrared light — which means ambient light in the room can interfere with the reading and make a sensor misreport whether it's over the line. The robot was designed to move quickly without losing the line, including when lighting changed or a sensor got briefly covered — which meant the sensing and steering logic had to be trustworthy enough to react fast without second-guessing itself.

02 · Sensor Layout

Four sensors, each calibrated on its own

The array is four analog IR sensors — far-left, inner-left, inner-right, far-right — wired to analog pins A1, A3, A2, and A0 respectively, driving two motors on digital pins D9 (left) and D10 (right).

Fig. 1 — Four sensors with confirmed pins and thresholds. Sensor model is not verified.
Design Decision — Independent thresholds, not a shared one

The four sensors don't share a single threshold — I set one per sensor: 620, 480, 840, and 830. Sensors don't all sit at the same height, angle, or distance from the surface, and ambient light doesn't hit each one evenly, so a reading that means "on the line" for one sensor can mean something different for another. Calibrating each sensor individually was the difference between the robot reacting correctly and reacting to noise.

03 · Design Decision

Why priority-based steering

Design Decision — Priority cascade over uniform response

A simpler design would treat every sensor the same and react with one fixed turn strength. I chose a priority cascade instead — nine ordered checks, evaluated top to bottom, where the first matching condition wins. How far off the line the robot has drifted determines how sharply it turns: a single far sensor triggering gets a strong turn, both sensors on one side triggering together gets a very strong turn, and an inner sensor alone gets a small correction. That escalation is what let it react fast without overcorrecting past the line.

04 · Steering Decision Logic

The priority cascade, as implemented

Checked in order — first match wins, then a short brake before the next cycle:

  1. All 4 sensors black → Stop
  2. Both left sensors black (far-left + inner-left) → Very strong left 40 ms
  3. Both right sensors black (far-right + inner-right) → Very strong right 40 ms
  4. All 4 sensors white → Forward 18 ms
  5. Far-left black → Strong left 25 ms
  6. Far-right black → Strong right 25 ms
  7. Inner-left black → Small left correction 30 ms
  8. Inner-right black → Small right correction 30 ms
  9. Fallback (no case matched) → Stop

Every cycle ends with a 20 ms brake before the next read, regardless of which case fired.

Control logic, as implemented 
// Sensors (analog)
farLeft    = A1   // threshold 620
innerLeft  = A3   // threshold 480
innerRight = A2   // threshold 840
farRight   = A0   // threshold 830

// Motors
leftMotor  = D9
rightMotor = D10

if (all4 == BLACK)                    stop()
else if (farLeft & innerLeft == BLACK)   veryStrongLeft(40)
else if (farRight & innerRight == BLACK) veryStrongRight(40)
else if (all4 == WHITE)                  forward(18)
else if (farLeft == BLACK)               strongLeft(25)
else if (farRight == BLACK)              strongRight(25)
else if (innerLeft == BLACK)             smallLeft(30)
else if (innerRight == BLACK)            smallRight(30)
else                                     stop()

brake(20)  // every cycle

05 · Iteration & Tuning

What I tuned

I tuned the pulse duration behind each case by hand until tracking held up smoothly under the room's lighting: 40 ms for the very-strong turns, 25 ms for a single far sensor, 30 ms for an inner correction, 18 ms for forward, and a 20 ms brake after every cycle regardless of which case fired. The gap between the tiers — 40 ms down to 25 ms down to 30 ms rather than one shared number — reflects how urgent each case actually is: losing the line on both sensors at once needs more correction than a single inner sensor drifting slightly.

What these values replaced, and how many tuning passes it took to land on them — not documented.
06 · Testing

How I checked it

Testing was empirical: run the robot on the track under the competition's actual lighting, watch where it lost or held the line, and adjust. I don't have logged trial data or lap times from that process to cite here.

08 · Lesson

What I learned, what I'd improve

I learned that treating every sensor identically is the easy path and the wrong one — the cascade only worked because sensor position carried meaning about how urgent the correction was. With more time, I'd log tuning runs as I went, the way I have on later projects, instead of relying on memory afterward — this write-up would be more specific if I had.
